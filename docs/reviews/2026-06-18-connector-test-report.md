# Workout Connector — Test, Analysis & Recommendations

**Prepared:** 2026-06-18 · **Scope:** All 33 `workout:*` tools · **Account:** Garron (admin)
**Evaluation lens:** Fitness for purpose as a *scientific personal trainer* — a system that should deeply and accurately understand a user's training, strengths, weaknesses, progress, and setbacks.

---

## 1. Executive summary

The connector is **strong and unusually well-engineered**, especially its engine-transparency layer. The data model (macro → meso → microcycle → workout, with per-set logging, feedback scales, and a versioned prescription engine) is exactly what a scientific coach needs. Decision rationales are human-readable, the tuning workflow (propose → replay → simulate) is genuinely safe, and grounding tools like `get_training_overview` are excellent.

However, the suite is **not yet fully reliable for autonomous coaching**. One flagship tool is broken, several analytics tools disagree with each other on the same underlying numbers, and the scientific "guardrails" a coach relies on (volume landmarks, feedback-scale context, progress-metric definitions) are inconsistently exposed.

**Overall grade: B (solid, with one critical defect and a cluster of consistency gaps).**

| Dimension | Rating |
|---|---|
| Data depth & model | A |
| Engine transparency / tuning safety | A |
| Tool reliability | C+ (one tool broken, one opaque error mode) |
| Cross-tool consistency | C (conflicting metrics, sparse `data_quality`) |
| Scientific completeness | B− (no volume landmarks; undocumented metric math) |
| Write safety / reversibility | C+ (good guards, but no delete/undo) |

## 2. Methodology & coverage

Every tool was exercised against live data. Tools were graded on whether they (a) executed, (b) returned correct, internally consistent data, and (c) delivered something a scientific coach can actually act on.

**Reversible writes** were round-tripped and **restored** (set → verify → clear). **Irreversible or production-affecting writes were deliberately not executed** and were assessed by schema/design only — this is itself a finding (see §5.8).

## 3. What it does well

- **`get_training_overview` is the model citizen.** A single call returns who the user is, exactly where they are (macro → meso → week → next workout + target RIR), adherence, fatigue, and key-lift trend. This is the right "start here" primitive.
- **Engine transparency is best-in-class.** `get_engine_params` returns the full parameter set *and* a `resolved` merged view with `hash_verified: true`. `get_engine_decisions` exposes the engine's actual inputs, output, and a plain-English rationale (e.g. *"+5 lb: did 245×10 vs 250×10 prescribed at 1 RIR; target RIR steps 1 to 0"*). This is precisely the auditability a "scientific" claim requires.
- **The tuning loop is genuinely safe.** `propose_engine_params` writes an **inactive**, zod-validated version; `replay_decisions` re-runs real history against it read-only (with `rule_coverage` and per-outcome counts); `simulate_prescriptions` probes hypotheticals and **isolates invalid cases per-item** instead of failing the batch. Activation is a separate, explicit, echo-confirmed step. New proposals also capture a `code_sha` for provenance.
- **`compare_mesocycles` is honest.** It emits `warnings` (active/incomplete block, mismatched durations, differing deloads) and steers you to per-workout rates over raw totals — exactly the caveats a careful analyst would add.
- **`get_mesocycle_summary` sets the data-quality bar.** It is the only tool that returns a `data_quality` block with **sample sizes** and a **scales legend** (joint pain 0–3, pump 0–10, fatigue/effort/performance 0–4). Every numeric tool should look like this.
- **Reversible writes behave correctly.** `log_note` round-trips and an empty body clears; `manage_exclusions` add/remove is clean and immediately reflected.

## 4. Live-data sanity check (does the analysis hold up?)

Spot-checking the numbers against raw history shows the engine math is largely **coherent**:

- **Deadlift decision** — prescribed 250×10 @1 RIR, logged 245×10, engine output "+5 lb, RIR steps 1→0." Correct autoregulation logic.
- **Macro target** — for an intermediate at 159 lb, the 1.6–2.4 lb/month gain target reconciles with the engine's `hypertrophy_base_pct_bw_month` (1.0–1.5% of body weight). Internally consistent.
- **e1RM estimates** — latest Dumbbell Curl e1RM of 27 matches 20 lb × 11 reps under an Epley-style formula. The math checks out.

But the same spot-check surfaced the consistency problems in §5.

## 5. Defects & gaps (prioritized)

### 5.1 🔴 Critical — `get_exercise_affinity` is broken in 2 of its 3 modes
The tool documents three usage modes: no-args, filter by `equipment`, filter by `muscle_group_id`.
- No-args → **error**
- `equipment: "dumbbell"` → **error**
- `muscle_group_id: <uuid>` → ✅ works

Both failing calls returned an **opaque `[object Object]`** with no message. This is the connector's *primary* "which movements does this person actually tolerate and progress on" tool — the heart of personalized exercise selection — and its most natural call (no-args, "show me my whole affinity profile") fails. By contrast, `search_exercises` accepts the same `equipment` filter without issue, so the defect is local to this tool's non-`muscle_group_id` query path.
**Fix:** repair the no-arg / equipment-only query paths; return a structured error message, not a stringified object.

### 5.2 🔴 Critical — analytics tools disagree on the same numbers
For Dumbbell Curl (`22c73c4a…`):
- `analyze_exercise_progress` → `times_trained: 144`, `sessions: 144`
- `get_exercise_history` → `session_count: 43`

A **3× discrepancy** on fields that both read as "sessions." Separately, the **progress percentage** for this lift is reported as **−18%** (`overview`, `mesocycle_summary`) but **−15.9%** by `analyze_exercise_progress` — and that −15.9% doesn't reconcile with its *own* payload (first e1RM 33 → latest 27 = −18.2%). The change-percent definition (window? regression slope? best-vs-latest?) is undocumented and differs by tool.
**Impact:** a coach citing "you're down 16%" vs "down 18%" vs "144 vs 43 sessions" loses credibility instantly.
**Fix:** define each metric once (name the window and formula), reconcile `times_trained` vs `session_count` (or relabel one as "sets logged"), and surface the definition in the payload or `note`.

### 5.3 🟠 High — `data_quality` and the scales legend are missing almost everywhere
The schema clearly *supports* `data_quality` and top-level `units`, but only `get_mesocycle_summary` populates them; everywhere else they are `null`. So `get_recent_sessions` and `get_exercise_affinity` return raw `fatigue: 2`, `pump: 5`, `jointPain: 0` **with no scale**. A 2 on a 0–4 scale is very different from 2 on 0–10.
**Fix:** attach the scales legend and sample sizes to every tool that emits feedback or estimate values.

### 5.4 🟠 High — no volume landmarks (MEV / MAV / MRV)
`get_muscle_balance` is admirably honest: *"MEV/MAV/MRV landmarks are not yet parameterized, so no per-muscle threshold is asserted."* It can therefore flag *relative* imbalance (chest 4 sets/wk, push:pull 1.7:1, hamstrings lowest at 3) but **cannot say whether a muscle is below maintenance volume**. For this user, chest sits at ~4 sets/week on a hypertrophy bulk — likely under MEV — yet the advisory flags hamstrings instead, purely on relative ranking. Volume landmarks are foundational to evidence-based hypertrophy programming; without them the "scientific" claim is incomplete.
**Fix:** parameterize per-muscle MEV/MAV/MRV (by experience level) in the engine params and let `get_muscle_balance` assert thresholds.

### 5.5 🟠 High — `explain_prescription` returns nothing on the most common question
For Dumbbell Curl (43+ logged sessions), it returned `found: false` because the engine only writes a prescription when a week is generated, and the most recently generated workout (W4·D2) was a **leg day** — so the curl's next prescription doesn't exist yet. The tool only surfaces the single latest generated week's decision. "Why did my curl number change?" — the canonical use case — therefore yields nothing.
**Fix:** fall back to the most recent *historical* decision for that exercise (the data exists in `get_engine_decisions`), rather than only the latest generated microcycle. -- ***Editors note:*** *There is a known issue in feedback data history for my user at this point in time. The workout history which exists up until 6/15/2025 was migrated and imported from a different application from which full feedback data was not exportable. Feedback has only been captured for sessions after this date, so some of the finidings in this section are expected*

### 5.6 🟡 Medium — opaque error serialization
Failed calls render as `[object Object]` instead of a message (seen on `get_exercise_affinity`). This blocks diagnosis and would confuse any downstream agent.
**Fix:** serialize errors to `{ code, message, detail }`.

### 5.7 🟡 Medium — unrounded float noise
Estimates print as `73.33333333333333`, `17.083333…`, `5.1230769230769235`. `analyze_exercise_progress` rounds; `affinity`, `mesocycle_summary`, and `compare_mesocycles` don't. Cosmetically this undercuts a "precise/scientific" product and is internally inconsistent.
**Fix:** round e1RM/volume/feedback means to 1 decimal (or whole numbers for e1RM) consistently.

### 5.8 🟡 Medium — no delete/undo for create/propose
`create_macrocycle`, `create_mesocycle`, `create_template`, `create_custom_exercise`, and `propose_engine_params` have **no paired delete**. Consequences:
- These tools can't be tested without leaving permanent residue (this QA left an undeletable inactive engine-params **v7**).
- A user who fat-fingers a custom exercise or macro can't fix it via the connector.
**Fix:** add delete/archive tools (or a `dry_run` flag) for each create/propose tool. 
***Editors note:*** *Just note that an exercise can't be deleted if it has logged sets, this would undermine the explicit rules that past workouts are cannot be changed.*

### 5.9 🟡 Medium — `search_templates` dead-ends
It returns template IDs and says *"use a template id to start a meso,"* but no tool instantiates a meso from a `template_id` — `create_mesocycle` requires a full hand-built day structure. The discovery path has no execution path.
**Fix:** add a `template_id` argument to `create_mesocycle` (or a `start_mesocycle_from_template` tool).

### 5.10 🟢 Low — incomplete planned-volume across weeks
`get_muscle_group_volume` for the active 5-week meso shows weeks 1–4 for leg groups but only 1–3 for upper-body groups. Because the engine autoregulates forward, the "planned" picture is uneven mid-meso, which can mislead a week-over-week volume read.
**Fix:** either project the full planned ramp for all groups, or label clearly that future weeks are "not yet generated."

### 5.11 🟢 Low — minor rationale & validation polish
- `simulate_prescriptions` labeled a set where the lifter *exceeded* prescribed reps at target RIR as a *"close miss"* (the hold-load behavior on a RIR step-down week is defensible, but the wording isn't).
- Its validation error is generic (`"invalid engine inputs"`) with no field-level detail — weak for an admin tuning tool.

### 5.12 🟢 Low — surfaced data hygiene the tool could flag
The connector faithfully returns user-data artifacts without comment: the active macrocycle is named "May 2026 – Jun 2026" but has `duration_months: 6` (engine *recommended* 4); two unplanned mesos share the name "Mesocycle 5"; unplanned mesos default to `days_per_week: 1`; and many sessions report fatigue/effort/performance all = 2 (possible default vs. genuine input). A coaching layer should detect and gently flag these.

## 6. Recommendations (prioritized)

**Now (blockers for trustworthy coaching):**
1. Fix `get_exercise_affinity` no-arg + equipment paths (§5.1).
2. Reconcile and document progress metrics; fix `times_trained` vs `session_count` (§5.2).
3. Replace `[object Object]` with structured errors (§5.6).

**Next (scientific credibility):**
4. Propagate `data_quality` + scales legend to all feedback/estimate tools (§5.3).
5. Parameterize MEV/MAV/MRV and let `get_muscle_balance` assert thresholds (§5.4).
6. Make `explain_prescription` fall back to the latest historical decision (§5.5).

**Then (polish & lifecycle):**
7. Round floats consistently (§5.7).
8. Add delete/undo (or `dry_run`) for create/propose tools (§5.8).
9. Wire templates → `create_mesocycle` (§5.9).
10. Add a lightweight "data hygiene" advisory that flags naming/duration/default-feedback anomalies (§5.12).

---

## 7. Bottom line

As an **instrument panel**, this connector is excellent — the data is deep, the engine is transparent and auditably versioned, and the tuning workflow is safe by design. As an **autonomous scientific coach**, it is held back by one broken flagship tool, metrics that don't agree across tools, missing volume science, and feedback numbers presented without their scales. Close the three "Now" items and propagate the `data_quality` pattern that `get_mesocycle_summary` already nails, and this moves from *"a very good training database with a smart engine"* to *"a coach you can actually trust to reason about a person's training unsupervised."*
