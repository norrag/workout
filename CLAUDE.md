## Stack

Next.js (App Router) + TypeScript + Tailwind, Supabase (Postgres/Auth/RLS), Vercel, MCP server at `/api/mcp`.

## Hard rules

1. **RLS on every table, default deny.** Schema changes ship with policies and RLS tests in the same migration/PR.
2. **Migrations are append-only** in `supabase/migrations/`; never edit applied migrations or change schema via dashboard.
3. **The engine (`src/lib/engine/`) is pure.** No I/O, no dates-from-now, no randomness inside; all tunables come from `engine_params`. Every behavior change needs a unit/golden test.
4. **Service-role key only in `src/lib/supabase/service.ts`** call sites, always with explicit user scoping. Never in client bundles.
5. **MCP tools never take a `user_id` argument** — identity comes from the auth session only. Write tools create drafts; no deletes of logged history.
6. **Validate every boundary with zod** (forms, route handlers, MCP tool args, engine params).
7. **Design discipline (per 08):** light ledger system — cream `#F4F0E6` / ink `#17140F`; orange `#C14B2A` marks current position + selection only; square corners everywhere, dashed borders = planned/empty; lowercase logotype + tracked all-caps labels; no hype copy, no exclamation marks.
8. **Pixel fidelity to the mockups is mandatory.** Before building or changing ANY screen, open `docs/design/mockups/workout - App Screens v2.dc.html`, find the figure (see the 08 §5 index), check `docs/09-design-changelog.md` for any dated amendment to it, and transcribe its exact structure, control patterns, copy, sizes, weights, and colors — never improvise a layout or label from the spec prose alone. Cross-check `docs/design/screenshots/`. The **mockup is the source of truth over the interactive prototype** (`WorkoutApp.dc.html` / `workout - Interactive Prototype.dc.html`) — where they diverge, follow the mockup. The dark theme in the prototype is exploratory (dark mode is out of scope). Deviate only where a hard rule forces it (e.g. no deletes of logged history) and record the deviation in `docs/PROGRESS.md`.
9. **Online reads, queued set-logging writes; no admin UI.** Reads are online-only — nothing beyond immutable build assets is runtime-cached (R7), and an offline navigation gets `/~offline`. **Set-logging writes go through the durable client-side queue** (`src/lib/logging/queue.ts`; 02 §A5, N68), which reversed the original no-outbox call: a tap enqueues and the UI advances immediately, so a stalled write can never strand the session mid-set. Queued ops must stay idempotent (deletes/unlogs stay foreground). Engine inspection/tuning/replay ship exclusively as admin-gated MCP tools.
10. **A user-visible change updates the Guide in the same PR.** The in-app User Guide (`src/content/manual/`) documents **live** behavior, so a PR that changes what a user sees — a screen, a control, a label, a number, or an `engine_params` activation, which moves behavior with no code diff at all — updates the chapter that documents it **and** that chapter's rows in `docs/22a-manual-claims.md`. The ledger's *source of truth* column is the index from code back to prose: grep it for the file, symbol or parameter path you touched, then re-verify every row that comes back — re-date it, or fix the prose and the row together. New claims get new rows; a new in-app link into the Guide also gets its rows in `src/lib/guide-links.ts` and `docs/22e-link-placement-audit.md`. Shipping the behavior and leaving the chapter stale is an incomplete change, and the only kind nothing in the diff will tell you about (doc 22 §8.3, Phase 8).

## Conventions

- snake_case in SQL; camelCase in TS; DB types generated, domain types in `src/lib/types/`.
- Data access goes through `src/lib/queries/` — no inline supabase queries in components.
- Stats screens and MCP must share the same views (`v_exercise_history`, `v_meso_summary`, `v_meso_week_muscle_sets` — role-grain facts weighted through `engine/volume.ts::fractionalSetCount`, one counting definition — `v_exercise_prs`, plus `v_exercise_overview` and `v_macro_summary` per the 09 deltas) — one definition of progress. (`v_meso_week_sets` was retired with R23, migration `20260703000003`.)
- Keep `main` deployable; vertical-slice PRs.

## Claude response style (Claude-specific — not a cross-agent convention)

> Scope note for anyone maintaining agent instructions for this repo: this
> section is about how **Claude** writes responses, not about the codebase. If
> the repo ever grows a generic `AGENTS.md` for other coding agents, this
> doesn't need to be copied there — it's addressing a tic specific to Claude
> models, not a house style every agent should share.

Don't close out finished work by manufacturing a matched pair of follow-up
issues to sound thorough. The specific pattern to avoid: ending a response with
"two things you should know," "two corrections in passing," "one issue to flag
before I go," etc. as a reflex, on every response, regardless of whether
anything is actually wrong. That turns one completed task into an implied
backlog of two more, and it reads as hedging dressed up as transparency — "done,
but—" instead of "done."

Real issues are still worth raising — a defect that changes the answer, a
decision only the user can make, a risk they'd want to know about before it
bites them. Say those plainly, in however many sentences they take, when they're
genuinely there. It is not an obligation to find two of them after every task.
